# Requirements Document

## Introduction

This spec defines property-based tests for the mirror domain value objects (FileEntry, SyncDecision, DownloadResult) and the PackagesParser. These tests validate formal correctness properties that go beyond the existing example-based unit tests, using Hypothesis to exhaustively explore input spaces and surface edge cases.

Two new test files will be created:
1. `tests/properties/domain/mirror/test_mirror_values_properties.py` — properties for value object invariants
2. `tests/properties/domain/mirror/test_packages_parser_properties.py` — properties for PackagesParser.parse()

## Glossary

- **Value_Object**: A frozen dataclass instance (FileEntry, SyncDecision, or DownloadResult) that is immutable after construction.
- **FileEntry**: A frozen dataclass with fields relative_path (str), sha256 (str), and size_bytes (int).
- **SyncDecision**: A frozen dataclass with fields file_entry (FileEntry), action (Literal["download","skip","verify"]), and reason (str).
- **DownloadResult**: A frozen dataclass with fields url (str), success (bool), sha256_verified (bool), bytes_transferred (int), error (str|None), retry_count (int), status_code (int|None), and response_headers (dict[str,str]|None).
- **PackagesParser**: A class whose parse(content: str) method extracts FileEntry instances from Debian Packages index content.
- **Stanza**: A block of Key: Value lines in Packages file format, separated from other stanzas by one or more blank lines.
- **Valid_Stanza**: A stanza containing Filename, SHA256, and Size fields where Size is a non-negative integer.
- **Property_Test**: A test that uses Hypothesis @given decorator with @settings(max_examples=200) to validate an invariant over randomly generated inputs.

## Requirements

### Requirement 1: Value Object Immutability

**User Story:** As a developer, I want property tests that prove value objects are immutable, so that I can be confident frozen dataclass semantics hold for all generated instances.

#### Acceptance Criteria

1. FOR ALL generated FileEntry instances, WHEN attribute assignment is attempted on each of its fields (relative_path, sha256, size_bytes), THE Property_Test SHALL confirm that an AttributeError is raised for every field.
2. FOR ALL generated SyncDecision instances, WHEN attribute assignment is attempted on each of its fields (file_entry, action, reason), THE Property_Test SHALL confirm that an AttributeError is raised for every field.
3. FOR ALL generated DownloadResult instances, WHEN attribute assignment is attempted on each of its fields (url, success, sha256_verified, bytes_transferred, error, retry_count, status_code, response_headers), THE Property_Test SHALL confirm that an AttributeError is raised for every field.

### Requirement 2: Value Object Equality Reflexivity

**User Story:** As a developer, I want property tests that prove equality is reflexive for value objects, so that I can be confident every instance equals itself.

#### Acceptance Criteria

1. WHEN a FileEntry instance is generated by Hypothesis with arbitrary valid field values, THE Property_Test SHALL confirm that the instance equals itself using the == operator, across at least 200 examples.
2. WHEN a SyncDecision instance is generated by Hypothesis with arbitrary valid field values, THE Property_Test SHALL confirm that the instance equals itself using the == operator, across at least 200 examples.
3. WHEN a DownloadResult instance is generated by Hypothesis with arbitrary valid field values including both None and non-None combinations for optional fields (error, status_code, response_headers), THE Property_Test SHALL confirm that the instance equals itself using the == operator, across at least 200 examples.

### Requirement 3: Value Object Equality Symmetry

**User Story:** As a developer, I want property tests that prove equality is symmetric for value objects, so that I can be confident a == b implies b == a.

#### Acceptance Criteria

1. WHEN two distinct FileEntry instances are constructed with the same relative_path, sha256, and size_bytes arguments, THE Property_Test SHALL confirm that a == b and b == a both evaluate to True across 200 generated examples.
2. WHEN two distinct SyncDecision instances are constructed with the same file_entry, action, and reason arguments, THE Property_Test SHALL confirm that a == b and b == a both evaluate to True across 200 generated examples.
3. WHEN two distinct DownloadResult instances are constructed with the same url, success, sha256_verified, bytes_transferred, error, retry_count, status_code, and response_headers arguments (including None-valued optional fields), THE Property_Test SHALL confirm that a == b and b == a both evaluate to True across 200 generated examples.

### Requirement 4: Value Object Inequality on Differing Fields

**User Story:** As a developer, I want property tests that prove value objects with differing field values are not equal, so that I can be confident equality distinguishes by content.

#### Acceptance Criteria

1. FOR ALL pairs of FileEntry instances WHERE exactly one field (relative_path, sha256, or size_bytes) differs and remaining fields are identical, THE Property_Test SHALL confirm that a != b, repeating for each of the 3 fields independently.
2. FOR ALL pairs of SyncDecision instances WHERE exactly one field (file_entry, action, or reason) differs and remaining fields are identical, THE Property_Test SHALL confirm that a != b, repeating for each of the 3 fields independently.
3. FOR ALL pairs of DownloadResult instances WHERE exactly one field (url, success, sha256_verified, bytes_transferred, error, retry_count, status_code, or response_headers) differs and remaining fields are identical, THE Property_Test SHALL confirm that a != b, repeating for each of the 8 fields independently.
4. WHEN any inequality property test executes, THE Property_Test SHALL use hypothesis with @settings(max_examples=200) and generate field values consistent with the declared types in the value object dataclass definitions.

### Requirement 5: PackagesParser Idempotency

**User Story:** As a developer, I want a property test proving that parsing the same content twice yields identical results, so that I can be confident the parser has no hidden state.

#### Acceptance Criteria

1. WHEN PackagesParser.parse(content) is called twice on the same PackagesParser instance with the same content string, THE Property_Test SHALL confirm that both invocations return lists of FileEntry that are equal in length, order, and element values.
2. THE Property_Test SHALL generate content inputs using both a strategy that produces arbitrary strings (including empty, whitespace-only, and non-Packages text of up to 10,000 characters) and a strategy that produces valid Packages-formatted stanzas containing between 1 and 50 entries, and SHALL execute with @settings(max_examples=200).
3. IF a generated content string causes the first parse() call to return a non-empty list, THEN THE Property_Test SHALL confirm that the second parse() call returns a list with the same number of FileEntry elements, each having identical relative_path, sha256, and size_bytes values at the same list index.

### Requirement 6: PackagesParser Output Validity

**User Story:** As a developer, I want a property test proving that every FileEntry returned by the parser has valid field values, so that I can be confident the parser never produces malformed entries.

#### Acceptance Criteria

1. FOR ALL generated content strings consisting of both structured Packages-like stanzas and fully random text, WHEN PackagesParser.parse(content) is called, THE Property_Test SHALL confirm that every returned FileEntry has a relative_path with length greater than or equal to 1.
2. FOR ALL generated content strings consisting of both structured Packages-like stanzas and fully random text, WHEN PackagesParser.parse(content) is called, THE Property_Test SHALL confirm that every returned FileEntry has a sha256 with length greater than or equal to 1.
3. FOR ALL generated content strings consisting of both structured Packages-like stanzas and fully random text, WHEN PackagesParser.parse(content) is called, THE Property_Test SHALL confirm that every returned FileEntry has a size_bytes value greater than or equal to zero.
4. FOR ALL generated content strings, WHEN PackagesParser.parse(content) returns an empty list, THE Property_Test SHALL treat the output validity property as satisfied (vacuous truth).

### Requirement 7: PackagesParser Stanza Count Bound

**User Story:** As a developer, I want a property test proving that the parser never returns more entries than the number of stanzas in the input, so that I can be confident it does not fabricate entries.

#### Acceptance Criteria

1. FOR ALL generated content strings, WHEN PackagesParser.parse(content) is called, THE Property_Test SHALL confirm that the number of returned FileEntry instances is less than or equal to the number of stanzas in the input, where a stanza is defined as a maximal consecutive sequence of lines that are not blank (a blank line is one whose stripped form is the empty string), and stanza count is computed by splitting the content on lines, grouping consecutive non-blank lines, and counting the groups.
2. FOR ALL generated content strings that are empty or contain only whitespace characters, WHEN PackagesParser.parse(content) is called, THE Property_Test SHALL confirm that the returned list is empty (zero FileEntry instances).

### Requirement 8: PackagesParser Monotonicity

**User Story:** As a developer, I want a property test proving that appending a valid stanza to content does not decrease the result count, so that I can be confident valid data is never dropped.

#### Acceptance Criteria

1. FOR ALL generated content strings (including empty strings, arbitrary text, and text containing other valid or invalid stanzas) and FOR ALL generated valid stanzas containing a non-empty Filename value, a 64-character lowercase hexadecimal SHA256 value, and a Size value between 0 and 999999999 inclusive, WHEN the valid stanza is appended to the content separated by "\n\n" (or used directly if content is empty), THE Property_Test SHALL confirm that parse(combined) returns at least as many entries as parse(content).
2. IF the content string is empty, THEN THE Property_Test SHALL use the valid stanza alone as input (without a leading blank-line separator) and confirm that parse returns at least 1 FileEntry.

### Requirement 9: PackagesParser Round-Trip for Valid Stanzas

**User Story:** As a developer, I want a property test proving that generated valid stanzas are faithfully parsed into corresponding FileEntry instances, so that I can be confident the parser correctly handles well-formed input.

#### Acceptance Criteria

1. FOR ALL generated FileEntry values WHERE relative_path is a non-empty string containing no newline or colon characters, sha256 is a non-empty string containing no newline or colon characters, and size_bytes is a non-negative integer, WHEN a valid stanza string is constructed in the format "Filename: {relative_path}\nSHA256: {sha256}\nSize: {size_bytes}\n" and parsed by PackagesParser, THE Property_Test SHALL confirm that the resulting list contains exactly one FileEntry and that its relative_path, sha256, and size_bytes fields are equal to the originally generated values.
2. FOR ALL generated FileEntry values meeting the constraints in criterion 1, WHEN a valid stanza string is constructed and parsed by PackagesParser, THE Property_Test SHALL confirm that the test executes with Hypothesis settings max_examples of at least 200.

### Requirement 10: PackagesParser Error Conditions

**User Story:** As a developer, I want property tests proving that invalid stanzas are correctly rejected, so that I can be confident malformed input does not produce spurious entries.

#### Acceptance Criteria

1. FOR ALL generated stanzas that contain at least 1 other valid Key: Value line (e.g., Package, Version, Architecture) but omit the Filename field, WHEN PackagesParser.parse is called with that stanza as the sole content, THE Property_Test SHALL confirm that the returned list contains no FileEntry.
2. FOR ALL generated stanzas that contain at least 1 other valid Key: Value line but omit the SHA256 field, WHEN PackagesParser.parse is called with that stanza as the sole content, THE Property_Test SHALL confirm that the returned list contains no FileEntry.
3. FOR ALL generated stanzas that contain at least 1 other valid Key: Value line but omit the Size field, WHEN PackagesParser.parse is called with that stanza as the sole content, THE Property_Test SHALL confirm that the returned list contains no FileEntry.
4. FOR ALL generated stanzas that include Filename, SHA256, and a Size value that is not parseable as an integer (e.g., alphabetic strings, floats, empty strings, or special characters), WHEN PackagesParser.parse is called with that stanza as the sole content, THE Property_Test SHALL confirm that the returned list contains no FileEntry.
5. FOR ALL generated stanzas that include Filename, SHA256, and a Size value that is a negative integer (less than 0), WHEN PackagesParser.parse is called with that stanza as the sole content, THE Property_Test SHALL confirm that the returned list contains no FileEntry.
6. FOR ALL generated stanzas missing the Filename field, WHEN the invalid stanza is concatenated (separated by a blank line) with a valid stanza containing all required fields, AND PackagesParser.parse is called on the combined content, THE Property_Test SHALL confirm that exactly 1 FileEntry is returned corresponding to the valid stanza only.

### Requirement 11: Test Convention Compliance

**User Story:** As a developer, I want the property test files to follow the project's existing conventions, so that they integrate seamlessly with the test suite.

#### Acceptance Criteria

1. THE Property_Test files SHALL use the @pytest.mark.unit and @pytest.mark.mirror decorators on each test class.
2. THE Property_Test files SHALL use @settings(max_examples=200) on each test method.
3. THE Property_Test files SHALL include a module-level docstring describing the properties tested.
4. THE Property_Test files SHALL group related properties into test classes with class-level docstrings.
5. THE Property_Test files SHALL use hypothesis strategies (st.builds, st.text, st.integers, st.sampled_from) for input generation.
